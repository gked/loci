# Loci — Claude Instructions

## Project layout

```
app/                        React frontend
  design/                   Design system (tokens, assets, UI kit components)
src/loci/                   The installed package — imports are `loci.*`
  api.py                    Public facade used by the MCP server
  mcp_server.py             MCP tool definitions and docstrings; `loci-mcp` entry point
  http_server.py            FastAPI backend for the UI; `loci` entry point
  skill_assembly.py         read_skill/write_skill: procedure + user overlay
  skills_install.py         `loci skills`: writes the stubs into ~/.claude/skills/
  tools/                    Core business logic (registries, linting, writing)
  skills/
    references/             Canonical meta files seeded to vault/meta/ on init
      ontology.yaml         Type registry source
      relation-dictionary.yaml  Relation registry source
      ontology-user.yaml    User type extensions stub
      relation-dictionary-user.yaml  User relation extensions stub
      ontology-guide.md     User's guide to the ontology; seeded to vault/meta/
      ontology-system.md    Developer guide to the registries; never seeded
      <skill>-user.md       Skill overlay seeds; seeded once to vault/skills/, user-owned
    loci-save/SKILL.md      Save skill procedure (served live via read_skill)
    loci-query/SKILL.md     Query skill procedure
tests/                      Python test suite (outside the package — never ships)
  e2e/                      Browser end-to-end suite (Playwright) — see its README.md
  fixtures/vault/           Base fixture vault (unit suite; do not reshape)
  fixtures/e2e-overlay/     Extra nodes layered on top for e2e only
```

## Packaging rules

Loci is an installable wheel, not just a checkout. Two consequences bind every
change:

- **Runtime files must live under `src/loci/`.** Only that tree is packaged, and
  `deploy/Dockerfile` copies the same tree. Anything the code reads at runtime —
  above all `skills/references/`, which the registries load and `vault_init.py`
  seeds from — is missing on every installed machine if it sits outside.
  `test_ontology_guide_ships_inside_the_package` guards this.
- **Never reach for a repo path at runtime.** No `Path(__file__).parent.parent`
  walking up to the checkout root, and no reading `pyproject.toml` — an install
  has neither. Package metadata (`importlib.metadata`) is how `app_version()`
  answers; follow that pattern.

Imports inside the package are absolute (`from loci.tools.vault_init import …`).
There are no `sys.path` inserts anywhere in `src/` — don't reintroduce one to
make an import work; fix the import.

**The wheel carries the UI.** `app/` is not packaged, so the release build
compiles the bundle into `src/loci/static/` (`make wheel`) and `http_server`
serves it from there — that is how an installed Loci has a UI at all. The
directory is gitignored, so pyproject's `[tool.hatch.build] artifacts` entry is
what keeps it in the wheel; hatchling honours `.gitignore` and would otherwise
drop it silently. Never publish with a bare `uv build`.

Adding a console script means adding it to `[project.scripts]` in
`pyproject.toml` and giving it a `main()`. Keep `loci-mcp` and `loci` as
separate processes — see the docstring in `src/loci/__init__.py` for why.

## Skill ↔ Tool sync rule

**Always check both directions when touching either side.**

### When modifying Python tools (`src/loci/tools/`, `src/loci/api.py`, `src/loci/mcp_server.py`)

Ask: do the skill files need to reflect this change?

- New MCP tool added → check if any skill should call it and update the relevant SKILL.md
- MCP tool renamed or removed → update every SKILL.md that references it
- `read_meta` file map gains or loses a key → update skill instructions that call `loci__read_meta`
- New registry or validation added → check if skills need to read the new file or follow new rules
- Tool parameter or return shape changes → update skill steps that depend on that shape

### When modifying skill files (`src/loci/skills/`)

Ask: do the Python tools need to reflect this change?

- Skill references a `loci__read_meta` key that doesn't exist in `api.py` → add it
- Skill calls a tool with a parameter that doesn't exist → add or fix the parameter
- Skill describes behaviour (validation, enforcement) that isn't implemented → implement it or note it as aspirational
- Skill frontmatter changed (`name`, `description`) → the installed stub is stale; the release notes tell users to run `loci skills`

### How a skill reaches the model

A packaged `SKILL.md` never runs from `~/.claude/skills/`. What is installed
there is a **stub** generated by `skills_install.py` — the skill's frontmatter
(what Claude Code matches on) over a body that says "call `loci__read_skill`
and follow it". `read_skill` (`skill_assembly.py`) returns the packaged
procedure with the user's **overlay** appended: `vault/skills/<skill>.md`,
seeded once from `skills/references/<skill>-user.md`, never reseeded, written
by `write_skill` and nothing else. The preamble states the contract: the
overlay wins where it disagrees with the procedure, except under headings
marked 🔒, which hold regardless.

Consequences for a change to a skill:

- **No versions.** There is no `skill_version`, no version check, and nothing
  to bump. The server reads the file on every call, so a procedure edit is
  live on every install as soon as the package is.
- **Only the frontmatter reaches the stub.** Keep it to `name` and
  `description`; a change there is what makes `loci skills` have work to do,
  and `release_notes.py` reports it.
- **Mark what the user must not override.** A rule that exists for safety
  (ask before writing, verify the vault first) goes under a 🔒 heading. Every
  skill must have at least one; `test_skill_files.py` checks.
- **A new skill needs an overlay seed** — `references/<name>-user.md`, with the
  skill's name listed in `USER_SKILL_OVERLAYS`, plus a `META_VERSION` bump so
  existing vaults get it. The seed keeps the `-user` suffix; the copy in the
  vault drops it (`vault/skills/<name>.md`) — the directory already says whose
  it is.
- **Never symlink a skill into `~/.claude/skills/`.** A link serves the
  procedure directly and the overlay is never seen. `loci skills` replaces
  any symlink it finds with a stub, and there is no `--link` or `--force`.

### Meta file sync

`src/loci/skills/references/` is the source of truth. `src/loci/tools/vault_init.py` holds three lists, and which one a file belongs in follows from what it is:

- `META_FILES` — packaged substrate, reseeded to `vault/meta/` on every `META_VERSION` bump.
- `USER_META_FILES` — the user's *substrate* extensions, seeded once to `vault/meta/` and never overwritten. These extend a packaged registry and cannot override it (`type_registry._load_user` skips a colliding or inherited-field-redefining entry), so they sit beside the file they extend.
- `USER_SKILL_OVERLAYS` — the user's *policy*, seeded once to `vault/skills/<skill>.md` and never overwritten. These are meant to override the packaged half, 🔒 headings excepted. Different rules, different directory.

Don't merge the last two: `test_vault_init.py` fails with the reason.

When adding a new meta file:
1. Create it in `src/loci/skills/references/`
2. Add it to `META_FILES` or `USER_META_FILES` in `vault_init.py` (a skill overlay goes in `USER_SKILL_OVERLAYS` instead)
3. Bump `META_VERSION`
4. Add the key to the `file_map` in `api.py` → `read_meta()`
5. Update `mcp_server.py` docstring for `read_meta`
6. Update any skill that should read the new file

A seeded file must live under `src/loci/` — that is what the wheel packages and
what `deploy/Dockerfile` copies, so anything sourced from `docs/` is missing on
every installed machine and seeding fails. This is why the user's ontology guide
sits in `references/` rather than `docs/`. See Packaging rules above.

## UI impact check

**Always ask: does this change affect the UI?**

After any code change, check whether the `app/` frontend is affected:

- MCP tool added, renamed, or removed → does the UI call or display results from this tool?
- API response shape changes (new fields, renamed keys, removed fields) → does any React component consume this shape?
- New type, subtype, or relation added to the registry → does the UI render or filter on these values?
- Vault node schema changes (new/removed frontmatter fields) → does the UI read or display those fields?
- Business logic changes (sorting, filtering, validation) → does the UI rely on that behaviour?

If yes: inspect the relevant files under `app/` and update them (or flag to the user that UI changes are needed).

**Then run the e2e suite** (`make test-e2e`) — it is the enforcement mechanism
for this rule. If you changed a component the suite selects on, also update the
selector table in `tests/e2e/README.md`.

## Browser e2e suite

`tests/e2e/` drives the real app in Chromium against a real uvicorn
backend and a temp vault. **Read `tests/e2e/README.md` before touching
it** — it documents four traps that will otherwise cost you an hour (fixture
dates are rewritten per run; many fixture uids 404 on `/api/nodes/{uid}`; the
command palette shows recent nodes until search debounces; expected counts live
only in `vault_facts.py`).

Rules of thumb:

- Selecting on UI state → add a `data-testid`, never match on the Latin display
  text (`praeceptum · command` etc.), and record it in the README's table.
- Adding or removing a fixture node → update `tests/e2e/vault_facts.py`;
  `test_fixture_composition.py` fails first and tells you what changed.
- Need a UI state the base fixture vault lacks (archived, ghost, asset) → add a
  node to `tests/fixtures/e2e-overlay/`, **not** to `fixtures/vault/`
  (that one backs the unit suite and its counts are asserted on).

## Releasing

A release is a tag plus a wheel on a GitHub Release. One command does all of
it:

```
make release BUMP=patch|minor|major
```

It bumps the version, opens the PR, waits for the PR's checks, merges it,
pulls `main` and pushes the tag — so it blocks for as long as the e2e suite
runs. `main` is still never written to by hand: the version change lands as a
PR like everything else. What is automated is the waiting and the merge.

The wait is not a formality. `main` has no branch protection — the repo is
private on a free plan, so GitHub will not enforce required checks — which
means nothing server-side would refuse a merge on a red build. The wait in
`scripts/release.py` is the only thing that does.

The same release in halves, for when CI wants watching by hand or a one-step
run died partway:

```
make release-bump BUMP=patch|minor|major   # opens the version-bump PR
<merge it, then git checkout main && git pull>
make release-publish                       # tags the merged commit
```

**The bump moves the version in two files** — `pyproject.toml`, and the
version `uv.lock` records for the local `loci` package. `uv run` re-resolves
the lock the moment those disagree, and the first command to run `uv run`
after a bump PR was `make release-publish` itself, which dirtied the tree its
own clean-tree guard then refused to act on. `release.py` runs `uv lock` as
part of the bump; `test_the_repos_lockfile_agrees_with_pyproject` guards it.

The tag fires `.github/workflows/release.yml`, which refuses to build unless
the tag matches `pyproject.toml` (`scripts/release.py check`), then builds and
publishes with generated notes.

Two things other than the package version are user-visible, and
`scripts/release_notes.py` surfaces them in the notes automatically by diffing
against the previous tag:

- `META_VERSION` moved → the vault's meta files reseed on next start.
- a skill's frontmatter changed, or a skill was added → the stub in
  `~/.claude/skills/` is stale until they run `loci skills`. A change to the
  procedure below the frontmatter is served live and is not reported.

Nothing has to be done by hand for that, but it is the reason `META_VERSION`
must be bumped in the same PR as the change it describes.

## Branch and PR rules

`main` is never written to directly. Every change lands through a PR from a
branch. Local hooks in `.githooks/` enforce this — run `make hooks` once per
clone to install them (they block commits and merges on `main`, block pushes to
`main`, and run the unit suite before every push).

The same directory carries two hooks that are conveniences rather than gates:
`post-checkout` and `post-merge` run `loci skills --yes` when a branch switch
or a pull changed a `src/loci/skills/*/SKILL.md` or `skills_install.py` — the
two things a stub is built from. A procedure edit is already live through the
MCP server, so this exists for what the stubs cannot do for themselves — a
skill someone else *added*, a reworded description, or a reworded stub
template, which arrives with the pull and leaves `~/.claude/skills/` behind.
Changes under `skills/references/` don't fire it; no stub reads them. They never
fail the git command they are attached to; `LOCI_SKIP_SKILL_INSTALL=1` turns
them off.

**Every PR must carry tests:**

- **Unit tests — always.** Any behaviour change needs unit coverage in
  `tests/`. A PR with no test change is only acceptable for pure docs,
  comments, or formatting.
- **Playwright e2e tests — whenever the PR touches the UI.** If the change adds,
  alters, or removes anything a user sees or clicks in `app/`, it also needs a
  browser test in `tests/e2e/` that drives the real thing in Chromium and
  asserts on the visible result. See the e2e sections below for the traps and
  the `data-testid` rule.

"Touches the UI" includes changes that reach the UI indirectly — an API response
shape, a registry value the UI renders, a node field the UI displays. Use the
UI impact check above to decide.

Both suites must be green before opening the PR: `make test`. CI re-runs them on
every push and PR, so a red suite blocks the merge anyway.

### Workflow for a change

1. Branch off up-to-date `main`:
   `git checkout main && git pull && git switch -c my-branch`
2. Implement locally and run `make test`.
3. **When the work is done and both suites are green, push and open the PR
   without asking** — don't wait for sign-off, and don't stop to report the
   local result first: `git push -u origin my-branch` then `gh pr create`.
   Report the test results and the PR link together, once it's open.
   Still don't merge the PR yourself unless asked.

   If the suites aren't green, or the work is genuinely ambiguous and you'd be
   guessing at what was wanted, stop and say so instead of opening a PR.
4. **After the PR is merged, sync back to `main`:**
   `git checkout main && git pull && git branch -d my-branch`.
   Leave the repo on an up-to-date `main` before starting the next change.

### Fixing review findings on an existing PR

Steps 1–3 describe *new* work. When the task is addressing review findings on a
PR that is already open, there is nothing to create:

1. Check out that PR's branch (`gh pr checkout <n>`) — do **not** branch off
   `main` and do **not** open a second PR.
2. Fix, run `make test`, commit, and `git push`. The push updates the open PR.

Never review a PR by checking its branch out over the working tree
(`git checkout <ref> -- .`) — read it with `git diff`, `git show <ref>:<path>`,
or a worktree. Overwriting the tree risks the user's uncommitted work.

**If a finding turns out to be separate work — a different concern, a shared
file this PR had no reason to touch, a fix noticed along the way — stop and ask
before doing it.** Present it as a yes/no choice with the options; don't decide
unilaterally and report it afterwards, and don't fold it silently into the PR.
This holds even when the extra work looks obviously right or blocks the finding:
say what is blocked and let the user pick.

If the PR was stacked on another PR, check it after the base merges — GitHub
closes a PR whose base branch is deleted rather than retargeting it (this is what
happened to #51).

## Running tests

```
make hooks                       # one-time per clone: install .githooks/
make test                        # full suite: Python unit + browser e2e
make test-fast                   # unit only (-m "not e2e") — no Node/browser
make test-e2e                    # browser suite only
make e2e-install                 # one-time: download the Chromium binary
uv run pytest tests/ -v          # like make test, but skips the npm ci step
uv run pytest tests/test_foo.py  # single file
make test-cov                    # with coverage report
```

Tests use `LOCI_VAULT_ROOT` env var (set by the `tmp_vault` fixture in `conftest.py`)
to point registries and api calls at a temporary copy of `tests/fixtures/vault/`.

## Registry singleton pattern

`TypeRegistry` and `RelationRegistry` (and any future registry) use a module-level
singleton loaded on first call. Tests that exercise registry-dependent code must
reset the singleton before and after to avoid cross-test pollution:

```python
from type_registry import reset_registry
from relation_registry import reset_relation_registry

@pytest.fixture(autouse=True)
def clean_registries():
    reset_registry()
    reset_relation_registry()
    yield
    reset_registry()
    reset_relation_registry()
```

The `tmp_vault` fixture in `conftest.py` does this for `nx_graph` already — follow
the same pattern when writing tests for any registry-backed module.

## Fixture vault has no `meta/` directory

`tests/fixtures/vault/` contains only node files — no `meta/` subdirectory.
This is intentional: registries fall back to `src/loci/skills/references/` when
`vault/meta/<file>` is not found, so tests automatically use the canonical
source files without extra setup.

**Do not add a `meta/` directory to the fixture vault** unless a test specifically
needs to override a registry file. If you do add one, it must be complete — a
partial `meta/` dir will cause the registry to load the partial file instead of
falling back, which silently breaks other tests.

## Adding a new registry

When a new registry is needed (parallel to `TypeRegistry` / `RelationRegistry`):

1. Define the YAML schema in `src/loci/skills/references/<name>.yaml`
2. Create `src/loci/tools/<name>_registry.py` with a `<Name>Registry` class and
   `get_<name>_registry()` / `reset_<name>_registry()` singleton functions,
   mirroring the pattern in `src/loci/tools/relation_registry.py`
3. Add the YAML to `META_FILES` in `vault_init.py` and bump `META_VERSION`
4. Add the `read_meta` key in `api.py` and update the `server.py` docstring
5. Wire validation into `write_file.py` (block on write, warn on patch)
6. Add a lint check in `vault_linter.py`
7. Update any skill that should read or validate against the new registry
8. Add tests: happy path, unknown value blocked, patch warning returned, lint warning emitted
