# Loci Field Dictionary
# Semantic guidance for the save skill — what each field means, how to fill it,
# and behavioral instructions that cannot be expressed in schema alone.
#
# STRUCTURAL AUTHORITY: ontology.yaml
# Field names, types, required/optional status, and enum values are defined in
# ontology.yaml and enforced at runtime by the TypeRegistry.
# This file does NOT define structure — it explains it.
# If this file conflicts with ontology.yaml, ontology.yaml wins.
#
# What this file owns:
#   - Human-readable descriptions of what each field means
#   - Usage guidance (e.g. "consult tag-dictionary before adding new tags")
#   - Behavioral instructions (e.g. "when updated, archive the old value")
#   - Object schemas and examples for complex fields (affiliations, history)
#   - Domain taxonomy with descriptions

## Base Schema (all types)

field: uid
type: string
required: yes
description: 8-character hex identifier, generated by loci__generate_uid

field: type
type: enum
values: document | article | bookmark | conversation | project | task | event | entity | procedure | topic
required: yes
description: canonical type; determines folder and extra fields

field: title
type: string
required: yes
description: concise, descriptive title

field: author
type: string
required: yes
description: "self" for user content; entity name or UID for external content

field: language
type: string
required: no
description: >
  ISO 639-1 code of the body's primary language (e.g. ru, de, fr, zh, ja).
  Omit for English — only set when the body is not in English.

field: aliases
type: array
required: no
description: >
  Alternative names, transliterations, or translations of the title.
  Always include the English form when the title is non-English.
  Examples: ["Oleg Markeev"] for an entity titled "Маркеев Олег";
  ["Black Moon"] for an article titled "Чёрная луна".
  Also used for abbreviations and alternate spellings.

field: state
type: enum
values: active | archived
required: yes
description: >
  Lifecycle state of the node. active nodes appear in all graph queries and
  searches by default. archived nodes are invisible to the graphing layer
  unless the user explicitly requests them (e.g. "show archived tasks").
  Defaults to active on creation. To archive: patch state to archived and
  set archived_at to the current timestamp. To unarchive: patch state to
  active and set archived_at to null.

field: created_at
type: datetime
required: yes
description: ISO 8601 timestamp of creation

field: updated_at
type: datetime
required: yes
description: ISO 8601 timestamp; bumped on every patch

field: archived_at
type: datetime
required: no
description: ISO 8601 timestamp if archived; null otherwise

field: tags
type: array
required: yes
description: 3–6 freeform lowercase hyphenated tags; consult tag-dictionary before adding new ones

field: domains
type: array
values: technology-engineering | science-research | business-strategy | finance-economics | health-biology | philosophy-ethics | creativity-design | personal-development | current-events-society
required: yes
description: one or more domain categories from fixed taxonomy

field: summary
type: string
required: yes
description: one paragraph — what this is, why it matters, key insight

field: relations
type: array
required: yes
description: links to other vault items; each entry is {uid, type} where type is a relation verb (e.g. influences, belongs-to, authored-by)

field: references
type: array
required: yes
description: external sources; each entry is {url, title, source_type}

field: has_asset
type: array
required: no
description: >
  List of file variants attached to this vault node. Each variant represents
  a distinct format of the same conceptual artifact (e.g. PDF and HTML of the
  same document). Only set when this node carries or references an external file.
  Read scheme-dictionary before constructing has_asset entries to confirm valid
  schemes and their required fields.

  Structure:
    has_asset:
      - format: pdf           # required: file format identifier
        primary: true         # optional: marks the primary/preferred variant (default false)
        locations:            # required: at least one location entry
          - scheme: local     # required: scheme name — must appear in scheme-dictionary
            path: assets/<uid>.pdf  # scheme-specific required fields (see scheme-dictionary)
            priority: 1       # optional: lower number = preferred fallback order
          - scheme: s3
            bucket: my-backup
            key: <uid>.pdf
            priority: 2
      - format: html
        locations:
          - scheme: google-drive
            file_id: 1aBcD...

  Authoritative fields only — store only what cannot be derived (format, primary flag,
  scheme, scheme-specific identifiers, priority). Do NOT store mime_type, size_bytes,
  last_verified_at, modified_time, or registered_at — compute these at resolve time.

  NOTE: Production use of has_asset as a list lands in Phase 5 of the locations refactor.
  Until then, existing nodes may carry has_asset: true (legacy boolean form).

field: affiliations
type: array
required: no
description: >
  structured history of organizational relationships; each entry is:
    {organization, roles, from, to}
  where organization is a name or UID, roles is an array, from/to are YYYY or YYYY-MM-DD, and to is null if current.
  Owns all org+role history — do NOT duplicate into history[].
  Example:
    - organization: University of Sussex
      roles: [Researcher]
      from: 1995
      to: 2001
    - organization: University of Manchester
      roles: [Professor]
      from: 2001
      to: null

field: history
type: array
required: no
description: >
  general audit log for any field that changes over time, except organization (owned by affiliations).
  Each entry is: {field, value, from, to}
  where value is the old value, from/to are YYYY or YYYY-MM-DD, and to is null if still current.
  Example:
    - field: location
      value: Brighton, UK
      from: 1995
      to: 2001
    - field: website
      value: https://old-site.example.com
      from: 2000
      to: 2010

#### body_template (asset subtype:book)

Not a frontmatter field. Guidance for the Markdown body of book nodes only.
When creating a new `asset subtype:book`, use this structure for the body:

```markdown
## Bibliographic
- Published:
- Original language:
- Edition:

## About
<!-- What this book is about. For Russian books: one paragraph in English,
     one paragraph in Russian. -->

## Notes
<!-- Personal notes, connections to other books. Filled in over time. -->
```

Fill in known values at creation time; leave blank lines blank rather than omitting sections.

#### Summary convention (asset subtype:book)

Overrides the default "English-only" rule for `summary`:
- `language: en` books — English summary only (default rule applies).
- Non-English books (e.g. `language: ru`) — summary in **both** languages: English paragraph first, native-language paragraph second, in the same field.

Reason: Loci semantic search must find books from queries in either language.

Example (Russian book):
```yaml
summary: |
  Systematic guide to Yoga Nidra as taught by Swami Satyananda Saraswati —
  covers psychic sleep technique, rotation of consciousness, and use for
  deep relaxation and meditation.

  Руководство по йога-нидре — техника психического сна, ротация сознания,
  применение для медитации и релаксации.
```

## Asset-registry physical array

The asset-registry YAML for a physical (or dual digital+physical) asset may include
a `physical` array alongside `files`. Each entry in `physical` represents one
physical instance you own.

Schema per physical instance:
  format      string   required — what kind of physical object: paperback, hardcover,
                                  coin, vehicle, photo-album, print, instrument, etc.
  location    string   required — where it is: "Bookshelf A3", "Home garage", "Safe, drawer 2"
  condition   string   optional — freeform: new | mint | good | fair | poor | damaged;
                                  use grading notation for collectibles (e.g. MS-65 for coins)
  acquired_at string   optional — ISO 8601 date
  quantity    integer  optional — how many; defaults to 1 (useful for coins, prints)
  attributes  object   optional — freeform key-value dict for item-specific metadata
  notes       string   optional — any other details

Examples:

  # Physical book
  physical:
    - format: paperback
      location: "Bookshelf A3"
      condition: good
      acquired_at: '2019-04-01'
      attributes:
        edition: 3rd
        isbn: "978-0-13-468599-1"

  # Gold coins
  physical:
    - format: coin
      location: "Safe, drawer 2"
      condition: mint
      quantity: 3
      attributes:
        metal: gold
        weight_troy_oz: 1
        mint: Royal Canadian Mint
        year: 2019

  # Car
  physical:
    - format: vehicle
      location: "Home garage"
      condition: good
      acquired_at: '2021-03-15'
      attributes:
        make: Toyota
        model: Camry
        year: 2019
        vin: 1HGCM82633A123456
        color: Silver

  # Picture album
  physical:
    - format: photo-album
      location: "Living room cabinet"
      condition: good
      attributes:
        period: "2005–2012"
        contents: "Family photos, childhood"

### log

field: subject_uid
type: string
required: yes
description: >
  UID of the vault node this log is about — typically an asset subtype:book, topic, or project.
  A log cannot exist without a subject; subject_uid is a required direct reference, not just
  a relation. Also add an `about` relation pointing to the same UID for graph traversal.
  Note: the linter checks presence only — it does not verify the UID resolves to an existing
  vault node (no dangling-reference error, unlike dangling relations).

field: log_status
type: enum
values: in-progress | finished | abandoned
required: yes
description: >
  Current state of the engagement. Not content maturity — use state: archived to hide the node,
  not log_status: abandoned just because you stopped. abandoned means you intentionally quit.

field: started_at
type: datetime
required: no
description: ISO 8601 date when the engagement began

field: finished_at
type: datetime
required: no
description: ISO 8601 date when the engagement ended; null while in-progress

field: rating
type: string
required: no
description: personal rating — freeform (e.g. 5/5, 8/10, ★★★★)

field: highlights
type: array
required: no
description: notable excerpts, quotes, timestamps, or observations captured during the engagement
