# File Saving in Loci

Covers the `assets/` folder, the `loci-stage/` inbox, and how a file on disk
becomes a vault node.

---

## Directory layout

```
~/loci/                              ← loci_root  (_loci_root() in api.py)
  ├── knowledge-vault/               ← vault_root  (_vault_root())
  │   └── *.md                       (markdown nodes — text & frontmatter only)
  ├── assets/                        ← binary files live here
  │   ├── <uid>.<format>             (e.g. 56bb363e.pdf, a1cab730.png)
  │   └── .pending/                  (crash-recovery intent files)
  │       └── <uid>.json
  └── loci-stage/                    ← user inbox  (_stage_root())
      ├── <files to ingest>          (drop files here directly)
      └── .inbox-plan.yaml           (generated by scan_inbox)
```

Key rules:
- `knowledge-vault/` holds only `.md` files. No binaries ever go there.
- `assets/` is a **sibling** of the vault, not inside it.
- `loci-stage/` is a **sibling** of the vault, not inside it.
- The relative path stored in `has_asset` (`assets/<uid>.<ext>`) is always
  relative to `loci_root`, so it resolves correctly regardless of where the
  user's Nextcloud is mounted.

## Two ways to save a file

### A. Direct save — `save_asset`

Use when the file is already accessible on disk or is small enough to have been
read into the conversation context.

```
save_asset(
    source_path="/abs/path/to/paper.pdf",   ← server reads bytes directly
    format="pdf",
    mime_type="application/pdf",
    title="...",
    ...
)
```

Alternatively, pass `content=<bytes>` for files already in the conversation
context, or supply `content=<base64-string>` + `is_base64=True` via the MCP
tool (the MCP layer decodes it before calling `api.py`).
For large files (video, large PDFs) prefer the inbox workflow below.

**What happens inside `save_asset` (`api.py:363-495`):**

```
1. generate_uid()                          → e.g. "56bb363e"
2. if source_path given → read bytes from disk
3. compute paths
     asset_final  = assets/56bb363e.pdf
     asset_tmp    = assets/.pending/.56bb363e.pdf.tmp
     vault_path   = knowledge-vault/<slug>--56bb363e.md
4. write intent file                       → assets/.pending/56bb363e.json
     (crash-recovery: if we crash here the intent file lets server.py
      resume on next startup — server.py:64-95)
5. write asset atomically
     asset_tmp.write_bytes(content)        ← stage to temp
     asset_tmp.rename(asset_final)         ← atomic rename
6. build has_asset list
     - format: pdf
       mime_type: application/pdf
       primary: true
       locations:
         - scheme: local
           path: assets/56bb363e.pdf
7. write vault proxy node (*.md)
     includes has_asset in frontmatter
     body: "# {title}\n"
8. delete intent file                      ← cleanup
9. return {uid, asset_path, vault_path}
```

### B. Inbox workflow — `loci-stage/`

Use when you have many files to bulk-ingest, or files are too large to pass
through MCP (video, large ebook collections).

```
User drops files into loci-stage/
         │
         ▼
scan_inbox()           reads loci-stage/ (flat, skips subdirs)
                       classifies each item (ebook → ingest-asset, ambiguous → unresolved)
                       writes loci-stage/.inbox-plan.yaml
         │
         ▼
approve_inbox_plan()   marks plan approved
         │
         ▼
execute_inbox_file_batch()   processes up to budget_per_run.files items
  for each file:
    1. read file from loci-stage/<path>
    2. call save_asset() → writes to assets/, creates vault node
       (a title already in the vault is refused: the item is parked as
       `duplicate`, the file kept, and the existing node reported)
    3. delete file from loci-stage/
    4. update plan status
  returns {processed: [...], failed: [...], duplicates: [...], remaining: int}
```

Repeat `execute_inbox_file_batch()` until `remaining == 0`. A parked duplicate
keeps the plan open until `update_inbox_item()` resolves it — `status="skipped"`
to drop it, or `status="pending", allow_duplicate=True` to save a second copy on
the next batch.

## Vault node structure for an asset

```yaml
---
uid: 56bb363e
title: Research Paper on AI Safety
type: asset
subtype: book
tags: [ai, safety, research]
domains: [technology-engineering]
has_asset:
  - format: pdf
    mime_type: application/pdf
    primary: true
    locations:
      - scheme: local
        path: assets/56bb363e.pdf
---

# Research Paper on AI Safety
```

The vault node is a lightweight proxy — it carries all searchable metadata and
the location pointer. The actual bytes live in `assets/`.

---

## Asset resolution

When Loci needs to retrieve the actual file it calls `resolve_asset(uid)`:

```
resolve_asset(uid)
  → read vault node, extract has_asset list
  → for each location in order:
      scheme=local  → resolve path relative to loci_root
                      return {path, size_bytes, mime_type, metadata}
      scheme=*      → external pointer (google-drive, s3, nextcloud, …)
                      return metadata only; file access via native tool
```

Supported schemes: `local`, `url`, `google-drive`, `gmail`, `nextcloud`,
`icloud-drive`, `onedrive`, `dropbox`, `s3`, `ssh-remote`. All registered in
`src/loci/tools/resolvers/dispatcher.py`.

---

## Crash safety

Between step 4 (intent file written) and step 8 (intent file deleted) a crash
would leave an orphaned asset on disk with no vault node.

On MCP server startup, `server.py:64-95` scans `assets/.pending/` for any
leftover `.json` intent files and replays them — writing the missing vault
node before accepting any tool calls.
